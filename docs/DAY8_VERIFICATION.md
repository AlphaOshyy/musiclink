# MusicLink Day 8: artist verification

Artist identity requests: authenticated users submit stage name, official HTTPS page, platform and optional notes. Each request receives a random 96-bit one-time proof code. The artist publishes that exact code in their official bio/website, then an authorized MusicLink administrator checks it independently. Verification is NEVER automatic on link submission. Public badge is derived only from the user record `verifiedAt` and persists until admin revocation. Public profile exposes `verified`, `artistName`, and `platform` for verified users. Self account exposes role for an admin review page. Request content and proof codes are restricted to the artist and admin reviewers.

Routes: GET /api/verification/mine, POST /api/verification/request, GET /api/verification/admin/queue?status=pending, PATCH /api/verification/admin/:id {decision:"approve",confirmedOwnership:true,reason:""}, POST /api/verification/admin/:id/revoke {reason:"..."}. Admin privilege is checked in MongoDB on every admin request, not trusted from the client's JWT role. Admin accounts must be provisioned out of band, ordinary signups remain creators.

Reviewers must examine the official page, match artist name and code, and record rationale. Spotify / YouTube links alone are NOT accepted as identity proof. No credentials or ID documents should be collected. An approved artist cannot change their display name using ordinary profile editing. Admin revocation removes the badge. Only public HTTPS web addresses are accepted, with URL validation and no server-side fetching to avoid SSRF. Rate limits and unique artist request prevent basic spam.

Limitations: manually verified control, not proof of legal identity. Human review and admin provisioning remain operational steps. There is no fully automated OAuth ownership handshake or credentialed third-party artist authorization in this milestone. Admin review approval is stored across two MongoDB documents without a transaction; future audit-grade revisions should use transactions and an append-only review history. Tests cover policies, validation, and build.
